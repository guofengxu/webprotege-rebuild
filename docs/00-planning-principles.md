# 规划原则：为什么重来，这次怎么拆

## 背景

上一轮重构（IndustrialOntology 工程，wp-kernel / wp-domain / wp-ai 等模块）没能推进，直接原因是**任务拆解过粗**：交给 Agent 的任务只给了目标，没有给出边界、接口和验收方式，Agent 只能自行发挥，结果难以评审、难以集成。

这次改成新建空工程重写，并把规划本身当作交付物：先用逆向分析（REA）把旧系统的行为固定为可测试的规格，再按规格拆卡。

> 如果需要对照上一轮的任务清单，把它放到 `docs/archive/` 下即可，本规划不依赖它。

## 拆解原则

1. **一张卡 = 一个模块里的一个 PR。** 改动量预期 ≤ 400 行（不含测试和测试数据），一天内能完成。
2. **每张卡都写明产出物。** 列出具体文件、类名和关键方法签名，不写“实现 XX 功能”这种描述。
3. **验收必须可执行。** 每张卡至少有一条 `./mvnw ... -Dtest=...` 之类的命令，外加一组可勾选的完成判据。“代码写完”不算完成，测试通过才算。
4. **行为先于实现。** 凡是旧系统已有的语义（有效变更过滤、IRI 生成、回滚、层级计算等），先把语义写进 `docs/01-rea/behavior-specs.md`，任务卡引用规格编号，验收测试直接按规格写。旧工程里现成的 `*_TestCase` 优先移植。
5. **先竖切，后铺开。** P1 先打通一条完整链路：内存本体 → 变更流水线 → 修订日志 → 重放加载。功能广度放到后面。
6. **用门禁代替信心。** 依赖冲突、模块边界、性能这三类风险都有专门的卡和自动化检查，不靠评审时的感觉判断。
7. **滚动式规划，但不糊弄。** P0–P3 每张卡都写到可以直接开工；P4–P6 列出卡片清单和验收要点，由规划卡（`P4-00`、`P5-00`、`P6-00`）在前一阶段完成后细化。规划卡的产出同样要通过 `plan_lint` 校验。
8. **流程由脚本保证，提交由人确认。** 建分支、测试、更新状态、提交推送统一走 `tools/task.py`（`docs/04-dev-workflow.md`）；Agent 只做到暂存并生成确认单，提交与推送由人运行 `task.py commit` 触发；每类工作用哪些 ECC skill 由 `tools/ecc-routing.json` 规定，写进每张卡的「ECC 技能」小节。
9. **停下来是合法结果。** Agent 遇到歧义或范围外改动时，把卡标成 `blocked` 并写明原因（见 `AGENTS.md` 第 6 节）。被阻塞的卡由人拆分或修订后再继续。

## 卡片粒度自检

开卡前问自己四个问题，任何一个答“否”就继续拆：

- 能不能用一句话说清这张卡交付什么？
- 产出物能不能列成文件清单？
- 验收能不能写成命令？
- 别的 Agent 只读这张卡和它引用的文档，能不能做完？
