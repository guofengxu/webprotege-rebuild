# ADR-013 数据放置：本体模型、设计期实例与运行期实例

- 状态：已接受（实例库部分为“待 PoC 验证”）
- 日期：2026-10-29

## 背景

需要回答两个问题：用 PostgreSQL 作为本服务的存储是否合理？本体模型（TBox）和本体实例（ABox）能否都放在这个数据库里？

先明确本服务是什么：它是**设计期**的协同本体编辑器。它的数据和访问方式如下：

| 数据 | 写入方 | 写入频率 | 读取方式 |
|---|---|---|---|
| 修订日志、快照 | 人通过编辑器 | 每人每分钟几次 | 加载时顺序读取；按实体查历史 |
| 用户、权限、项目元数据、设置 | 人 | 很少 | 按主键查询 |
| outbox | 写修订时同一事务写入 | 同修订 | 发布器按顺序消费 |
| 本体查询（层级、Frame、搜索） | — | — | **不查数据库**，查内存模型和 Lucene（ADR-005、ADR-009） |

## 决策

### 1. 编辑器使用 PostgreSQL：合理，维持 ADR-004

上表全部是事务型、关系型的数据，PostgreSQL 完全胜任。编辑器对数据库**没有**图遍历、SPARQL 或推理的需求，因为这些查询都在内存中的 OWL API 模型上完成。所以“PostgreSQL 不是图数据库”对编辑器并不构成缺点。

### 2. 本体模型（TBox）：放在编辑器的 PostgreSQL 中

- 真源是 `revisions` 表中的修订日志（事件溯源），`snapshots` 用于加速加载。这一点已经由 ADR-004、ADR-011 确定。
- **不**把本体拆成“类表、属性表、公理表”这种关系模型作为真源：OWL 公理是嵌套表达式，关系化之后无法无损还原，而且会失去修订、回滚、差异对比这些依赖日志的能力。
- 如果外部系统（BI、AI Agent 的 SQL 工具）需要用 SQL 查询本体，P6 提供一份**派生的投影表**（实体、标签、父子关系、属性的定义域和值域），由 outbox 驱动更新，只读，可以随时重建。

### 3. 设计期实例：放在本体中，与 TBox 同库

设计期实例指建模时就确定、数量有限、变化缓慢的个体，例如：

- 枚举值：库存状态 QUARANTINE / RELEASED / REJECTED，温区 COLD_2_8 / AMBIENT；
- 参考个体：标准件、示例对象、用于说明模型的典型实例。

它们本来就是 OWL 个体，和类、属性一起编辑、一起版本化，放在同一个项目中最合理。

**规模约束**：一个项目的公理总数（TBox + 设计期实例）以 P1-20 基准验证过的规模为上限（初始目标为 50 万条公理）。超出时应该拆分项目，或者把实例移到实例库。

### 4. 运行期实例：不进编辑器，放到独立的实例库

运行期实例指业务系统持续产生和修改的对象，例如：18,000 个货位的实时状态、在库托盘、批次、出入库任务、AGV 与堆垛机的状态、质量事件。它们**不能**放进编辑器的修订模型，原因如下：

| 编辑器的设计 | 运行期实例的要求 | 冲突 |
|---|---|---|
| 每个项目单写者，写入串行（ADR-006） | EWM / WCS / AGV 系统并发写入，每秒可能有多次 | 吞吐量受限 |
| 每次写入产生一个修订，永久保留 | 状态频繁变化，绝大多数中间状态没有保留价值 | 修订日志膨胀，按实体查历史变慢 |
| 整个项目加载在内存中（ADR-005） | 实例数量随业务增长，没有上限 | 内存无法承受 |
| 修改者是人，有权限和审计 | 修改者是系统，需要的是集成接口和幂等写入 | 权限模型不匹配 |

运行期实例放在**实例库**中。实例库是一个独立的服务（P6），数据库同样选 PostgreSQL 18，但使用**独立的数据库**（例如 `wp_instances`），不与编辑器共用 schema：

- **模型**：`instances(iri, class_iri, attributes jsonb, valid_from, valid_to, source, ontology_rev)` + `links(subject_iri, property_iri, object_iri, valid_from, valid_to)`。类与属性一律用 IRI 引用编辑器中的本体；`ontology_rev` 记录写入时依据的本体修订号。
- **校验**：实例库订阅编辑器的 outbox。本体发布后，由 TBox 生成校验规则（属性的定义域和值域、必填属性、基数、枚举取值），写入时进行校验。
- **遍历**：1 ~ 3 跳的关系查询使用递归 CTE。深层追溯（例如“批次 → 托盘 → 货位 → 环境事件 → 设备”）如果递归 CTE 达不到性能要求，在实例库中启用 **Apache AGE**（PostgreSQL 的 openCypher 扩展；1.6 支持 PostgreSQL 17，1.7 与 1.8 支持 18），不需要另引入一个图数据库。
- **时序数据**：温湿度、遥测等高频数据不进实例库，继续放在 TDengine / StarRocks 等现有平台；实例库中只存“该货位的温度点位在哪张表、哪个 tag”这样的引用。

### 5. 什么情况下改用专门的图数据库或 RDF 三元组库

满足以下任一条件时，另开 ADR 评估 Neo4j / NebulaGraph（属性图）或 Jena Fuseki / GraphDB（RDF）：

- 需要在实例上执行标准 SPARQL 查询或 OWL 推理；
- AGE 的 PoC 中，代表性的深层追溯查询 p95 超过 1 秒；
- 关系边数量超过约 1 亿条，并且以多跳遍历为主要负载；
- 需要图算法（最短路径、社区发现等）。

## 理由

- 一种数据库技术覆盖编辑器和实例库两种负载，运维、备份、权限只有一套；编辑器本身不需要图能力。
- 编辑器与实例库分开数据库，负载和备份策略互不影响，也保住了编辑器“单写者 + 完整修订”的模型。
- 以天津诺和诺德仓库为例：约 1.8 万个货位、5 台堆垛机、7 ~ 8 台 AGV，在库托盘和每日任务在数万量级。这个规模在 PostgreSQL 上用普通索引即可支撑。

## 后果

- P6 新增候选项：“实例库服务 PoC（PostgreSQL 18 + 可选 AGE）”和“本体投影表”。
- 编辑器的 MVP 不受影响：实例库只通过 outbox 消费编辑器的修订。
- 需要在建模规范中明确哪些个体属于“设计期实例”，哪些属于“运行期实例”。判断标准：是否由业务系统产生或修改，以及数量是否会随业务量增长。
