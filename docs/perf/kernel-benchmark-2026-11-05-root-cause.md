# 内核基准未达标的根因分析（2026-11-05）

对应报告：[kernel-benchmark-2026-11-05.md](kernel-benchmark-2026-11-05.md)。对应卡片：P1-20（阻塞），修复卡 P1-22～P1-25。

## 结论

- 3 项未达标都来自内核里的实现缺陷，**不是** OWL API 自带索引的能力上限。ADR-005 的前提（内存读模型直接用 OWL API 索引）没有被推翻。
- 依据：不挂派生视图时，50 万公理单次编辑 p50 0.13 毫秒、p95 0.25 毫秒；重放 13.7 万条变更/秒；加载后堆占用 0.23 GiB。这些都远在门禁以内。
- 处理：开 4 张单模块修复卡（P1-22～P1-25），全部合并后重跑 P1-20。暂不修订 ADR-005 / ADR-011，也不为了性能启用 `ofn-lines/2`。重跑仍不达标时，按 ADR-005 新开 ADR。

## 根因与证据

分析机器比报告机器慢约 1.3 倍（同一份逐行解码实现，报告机器 3,203 行/秒，分析机器 2,385 行/秒）。下文的“分析实测”都是分析机器上的数字。

### 1. 快照解码 1,679 秒（门禁 ≤ 30 秒）→ P1-22

- 位置：`OfnZipSnapshotCodec.ignoreBracketIris`（由 `parse` 调用）。
- 机制：用正则 `<([^>\s]*)>` 抓出文档里**所有**尖括号 IRI（每个实体至少一个），逐个调用 `OWLOntologyLoaderConfiguration.addIgnoredImport`。OWL API 5.5.1 里这个配置对象不可变，每次调用都会复制整个已忽略集合，总成本 O(n²)。
- 编码同样受影响：`encode` 里的回读校验 `requireLossless` 也走 `parse`，所以 50 万公理编码也要 1,578 秒。
- 分析实测：

| 规模 | 忽略循环 | 解码合计 | 纯解析（不做忽略循环） | 正则本身 |
|---|---|---|---|---|
| 约 3 万公理 | 4.41 秒 | 4.41 秒 | 0.63 秒 | 0.011 秒 |
| 约 6 万公理 | 12.11 秒 | 12.85 秒 | 0.79 秒 | — |
| 约 50 万公理（修复后模拟：纯解析 + apply） | — | **11.48 秒** | 9.58 秒 | — |

- 修法：只把 `Import(<…>)` 声明里的 IRI 加入忽略列表（通常只有几个）。读取用的 manager 已经把所有文档 IRI 映射到 `urn:wp:snapshot:blocked-import`，并且设置了 `SILENT`，“不访问网络”的保证不变。

### 2. 单次编辑 p95 1,421 毫秒（门禁 ≤ 100 毫秒）→ P1-24、P1-25

- `ChangePipeline` → `RevisionLog.append` → `ProjectRuntime.applyCommitted` 这条核心路径本身没有问题。时间都花在派生视图的 `onApplied` 上，而且随项目规模线性增长：
  - `AbstractHierarchyView.onApplied` 每次编辑都执行 `entitiesIn(after)`，把整个项目签名物化成集合，只为判断受影响实体是否还存在。4 个层级视图各做一次。
  - `DisplayNameView.onApplied` 调用 `install(after, true)`，实际是完整重建：扫描全部 `AnnotationAssertion` 公理、给全部签名实体求名、对全部实体做差分，再 `Map.copyOf`。
- 分析实测（每次编辑给一个类加 `rdfs:label`，p50）：

| 启用的视图 | 约 6 万公理 | 约 12 万公理 |
|---|---|---|
| 无 | 0.15 毫秒 | 0.15 毫秒 |
| 只有类层级 | 39 毫秒 | 84 毫秒 |
| 4 个层级视图 | 38 毫秒 | 104 毫秒 |
| 只有显示名称 | 91 毫秒 | 188 毫秒 |
| 全部 5 个 | 95 毫秒 | 205 毫秒 |

  约 50 万公理、无视图时：p50 0.13 毫秒，p95 0.25 毫秒。
- 修法：层级视图改用 `ProjectOntologies.containsEntity(entity)`（已有方法，走 OWL API 索引）逐个判断受影响实体（P1-24）；显示名称视图改成只重算受变更影响的 IRI（P1-25）。修复后单次编辑只做按实体的索引查找。“p95 远低于 100 毫秒”是推算值，P1-25 没有做原型，以 P1-20 重跑为准。

### 3. 逐行解码 3,203 行/秒（门禁 ≥ 20,000 行/秒）→ P1-23

- 位置：`OfnLines.parseDocument` 每解码一行都调用 `manager(dataFactory)`。后者每次执行 `OWLManager.createOWLOntologyManager()`，新建 `OWLOntologyManagerImpl`，安装解析器和本体工厂，然后走一遍完整的文档加载流程。编码时的回读校验 `renderChecked` 也是每条变更走一次同样的路径。
- 分析实测（10 万行）：

| 做法 | 吞吐 |
|---|---|
| 现有实现 | 2,385 行/秒 |
| 只调用 `OWLManager.createOWLOntologyManager()`（不解析） | 4,063 次/秒 |
| 一次解码共用一个 manager，每行 `loadOntologyFromOntologyDocument` | 19,416 行/秒 |
| 一次解码共用一个 manager 和一个暂存本体，每行直接调用 `OWLFunctionalSyntaxOWLParser.parse` | **27,265 行/秒** |
| 把整段载荷当成一份文档解析（仅作上限参考，不采用） | 51,575 行/秒 |

- 修法：每次 `decode` / `encode` 调用只建一套解析上下文，所有行共用。每行的校验（恰好一条公理或注解、不允许导入声明、匿名个体编号不重映射）保持不变，`ofn-lines/1` 格式不变。

## 修复与重跑顺序

| 卡片 | 内容 | 依赖 |
|---|---|---|
| P1-22 | 快照编解码只忽略导入声明的 IRI | P1-07 |
| P1-23 | 逐行编解码共用解析上下文 | P1-06 |
| P1-24 | 层级视图增量更新不再物化全项目签名；新增 `CountingProjectOntologies` 测试支撑 | P1-18 |
| P1-25 | 显示名称视图增量更新 | P1-19、P1-24 |
| P1-20 | 重跑基准，产出新报告 | 上面 4 张 + 原依赖 |

P1-22、P1-23、P1-24 互不依赖，可以按任意顺序做。

## 测量方法说明

- 分析用的是临时探针程序（未纳入仓库），复用 wp-kernel 的测试类路径、`SyntheticOntologyGenerator` 和与 `KernelBenchmark` 相同的生成参数（分支系数 4，每个类 1 个语言标签，约 3 条公理/类），JDK 25，`-Xmx6g`。
- 探针数字只用来定位根因、估计修复效果。是否达标以 P1-20 在报告机器上重跑的结果为准。
