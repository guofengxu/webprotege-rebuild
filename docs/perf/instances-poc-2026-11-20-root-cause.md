# 实例库 PoC 基准未达标的根因分析（2026-11-21）

对应报告：[instances-poc-2026-11-20.md](instances-poc-2026-11-20.md)。对应卡片：P6-32（阻塞），修复卡 P6-53、P6-54。

## 结论

- 未达标的有 **3 项**：Q3 p95 94,403.54 毫秒（门禁 ≤ 200 毫秒）、W1 吞吐 167.6 次/秒（门禁 ≥ 200）、W1 单次写入 p95 93.66 毫秒（门禁 ≤ 50 毫秒）。Q1、Q2、Q4、Q5 和“两次运行行数一致”达标。P6-32 的阻塞记录只写了 Q3，漏了 W1 的两项。
- 主要根因是**测法缺陷**：`InstanceBenchmark` 用的是不带连接池的 `PGSimpleDataSource`，而 `TraceQueries` 和 `InstanceStore` 每次调用都会 `getConnection()`。所以每条 SQL 都要新建一条物理连接：TCP 连接、密码认证、PostgreSQL 新起一个后端进程，系统缓存也是空的。按报告中的数字反推，每次约 20 毫秒，比查询本身（Q1 执行 0.46 毫秒）大一个数量级以上。参照的 P6-18 基准用 `SingleConnectionDataSource` 复用一条连接，P6-32 没有沿用这一点。
- 放大因素是**生产代码的 N+1**：`TraceQueries.follow` 对前沿的每个节点各发一条查询。Q3 的一次调用发出 1 + 2,308 + 2,308 = 4,617 条 SQL，乘以每次约 20 毫秒的建连接开销，就是 94 秒。即使补上连接池，4,617 次往返仍要约 1 ～ 5 秒，Q3 还是不达标，所以生产代码也要改。
- W1 的两项未达标同样主要来自建连接：每次写入平均要建 1.6 次连接（约 32 毫秒），而报告中每次写入的平均耗时约 48 毫秒。
- 现有证据**推翻不了** ADR-013 的 `instances` + `links` 模型和 P6-31 的表结构，也不能作为评估 Apache AGE 的依据。本分析没有在机器上复现：分析机器上没有 Docker。上面的结论来自代码和报告中的数字；连接开销的直接测量由 P6-54 加进报告，在重跑 P6-32 时采集。
- 处理：开 2 张修复卡。P6-53 改生产代码，把 `follow` 改为每一跳一条 SQL；P6-54 改基准测法，改用连接池，并记录连接开销基线和 W1 的失败次数。两张都合并后重跑 P6-32，语料、规模、查询和门禁阈值都不改。

## 根因与证据

### 1. 每次调用都新建一条物理连接（测法缺陷，已从代码确认）

- `InstanceBenchmark.dataSource()` 返回 `PGSimpleDataSource`。它不做连接池，每次 `getConnection()` 都新建一条物理连接，`close()` 时断开。
- `TraceQueries.reachable`、`TraceQueries.neighbors`（`follow` 每一跳调用）、`InstanceStore.withTransaction`、基准自己的 `countSql` 和 `currentStoredAt`，每次调用都在 `try (Connection c = dataSource.getConnection())` 中执行。
- 新连接的代价：经 Testcontainers 映射端口的 TCP 连接；官方 `postgres` 镜像对网络连接默认使用 `scram-sha-256` 认证，客户端和服务端各要做一次 4,096 轮 PBKDF2；PostgreSQL 新起一个后端进程，它的系统表缓存是空的。报告中的执行计划可以佐证最后一点：Q1 这样一次索引扫描的计划，规划阶段就要读 186 个缓冲块（`Planning: Buffers: shared hit=186`），规划时间 1.15 毫秒，比执行时间（0.46 毫秒）还长。
- 按“每次调用一条新连接”反推，每次的固定开销都落在 20 ～ 22 毫秒，和查询的复杂度无关：

| 查询 | 一次调用发出的 SQL 条数 | p50 | p50 ÷ SQL 条数 | 执行计划中的执行时间 |
|---|---|---|---|---|
| Q1 | 1 | 22.79 毫秒 | 22.8 毫秒 | 0.46 毫秒 |
| Q2 | 1 + 3 = 4 | 87.00 毫秒 | 21.8 毫秒 | — |
| Q3 | 1 + 2,308 + 2,308 = 4,617 | 93,659.41 毫秒 | 20.3 毫秒 | — |
| Q5 | 1 | 26.85 毫秒 | 26.9 毫秒（其中执行 0.56、规划 4.73） | 0.56 毫秒 |

- 这一点偏离了 P6-32 卡片的参照：P6-18 的 `ProjectionBenchmark` 用 `SingleConnectionDataSource` 在一条连接上预热和采样。`wp-instances` 的 Enforcer 禁止依赖 `org.springframework*`，不能照搬这个类，所以 P6-32 退回到了 `PGSimpleDataSource`。
- 生产环境不会这样用：服务化之后（P6-34）一定有连接池。所以现在的数字测的是“建连接的开销 × SQL 条数”，不是实例库的查询能力。

### 2. `TraceQueries.follow` 是 N+1（生产代码，已从代码确认）

- `follow` 对每一跳、前沿中的每条路径的末端节点，各调用一次 `neighbors()`，每次一条 SQL（并且如上一节，每次一条新连接）。
- Q3 的路径是“堆垛机 →（`executedBy` 反向）任务 →（`moves`）托盘 →（`contains` 反向）批次”。语料中每台设备每天约 30,000 ÷ 13 ≈ 2,308 个任务，返回行数 2,308 与此吻合。所以一次 Q3 调用是 1 + 2,308 + 2,308 = 4,617 条 SQL。
- 补上连接池之后，每条 SQL 仍有一次网络往返加一次执行。按 0.3 ～ 1 毫秒估计，4,617 条约 1.4 ～ 4.6 秒，仍是门禁的 7 ～ 23 倍。所以只改测法不够，`follow` 本身要改成每一跳一条 SQL（`= any(?)` 批量取下一跳）。Q3 就从 4,617 次往返降到 3 次。
- 改完之后 Q3 能否达标没有直接证据，只能参照 Q4：Q4 的执行计划在同一张 `links` 表上做了 3,344 次索引查找，执行时间 78 毫秒。Q3 改完之后第 2、3 跳各做约 2,308 次索引查找，量级相近。要以重跑结果为准。
- Q1 走的是 `reachable`（一条递归 CTE），Q4、Q5 是单条 SQL，都不受 N+1 影响。它们现在的数字里大部分也是建连接的开销，补上连接池后会进一步下降。

### 3. W1 同样主要受建连接开销支配（测法缺陷，已从代码确认）

- 70% 的操作是 `upsert`：一次 `withTransaction`，即 1 条新连接。30% 的操作是移库：`currentStoredAt`、`unlink`、`link` 各一次，共 3 条新连接。平均每次操作 0.7 × 1 + 0.3 × 3 = 1.6 条，约 32 毫秒。
- 报告中 8 个线程共完成 167.6 次/秒，每个线程每次操作平均约 8 ÷ 167.6 ≈ 48 毫秒，其中约 2/3 是建连接。其余约 16 毫秒是事务本身（`select … for update`、`update`、`insert`、`commit`），以及 8 个线程同时建连接时在 8 个逻辑处理器上的 CPU 竞争（PBKDF2 和进程启动都是 CPU 密集的）。
- p95 93.66 毫秒约等于一次移库操作：3 次建连接加 3 个事务。
- 另外，W1 把失败的操作只记 debug 日志就丢掉了，报告没有失败次数。失败多时，吞吐被低估，p95 只代表成功的操作。这一点也由 P6-54 补上。

### 4. 阻塞记录不完整

- P6-32 卡片的「阻塞」小节只写了 Q3 未达标，写成“其余查询达标”；报告的门禁结论中 W1 的两项也未达标。报告路径被截断成了 `docs/perf/…`。本次拆卡时一并更正。

## 本轮不做的事

- 不在 P6-32 中优化，不改 `V1__instances_schema.sql`，不加索引，也不引入物化路径、闭包表或 Apache AGE。
- 不调 PostgreSQL 参数（`shared_buffers` 128 MB 等仍保持默认），不关闭 autovacuum 或 JIT。
- 不放宽门禁阈值。W1 的两个阈值是规划时的建议值，调整由人决定。
- 不把 Q4、Q5 的 SQL 提升为正式查询，那是 P6-34 的事。

## 重跑仍不达标时（由人决定）

先看新报告中的连接开销基线和执行计划，再按代价从低到高选择：

1. **Q3 仍超标，但单次往返已经是亚毫秒级**：说明三跳的批量查询本身慢。可以像 Q4 那样把 Q3 写成一条连接查询（由 P6-34 决定是否提升为正式查询），或者为 `links` 加覆盖索引。都需要新开卡。
2. **W1 仍超标**：先看失败次数和事务内的语句条数。可以在服务层合并写入（P6-34 规划），或者由人调整 W1 的两个建议阈值。不要用 `synchronous_commit = off` 这类参数换数字。
3. **深层追溯（Q4、Q5）反而超标**：按 ADR-013 第 4 节评估 Apache AGE，或另开 ADR。
